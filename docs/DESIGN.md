# MoveMgr 제품·기술 설계

작성일: 2026-09-29 · 설계 대상 첫 버전: 0.0.1 · 상태: 구현 인계용

## 1. 제품 정의와 핵심 결정

MoveMgr는 사용자가 등록한 프로젝트마다 소스 폴더의 파일을 선별하고, 파일명에서 분류값을 추출해 목적 폴더를 찾은 뒤 파일을 이동하는 로컬 데스크톱 앱이다. 사용자 표현의 ‘소스 프로젝트/타겟 프로젝트’는 각각 프로젝트 안의 **소스 폴더/타겟 폴더**로 명명한다.

프로젝트에는 이름, 소스·타겟 경로, 파일 조건, 분류값 추출법, 목적지 규칙, 충돌 처리 정책이 들어간다. 체크 상태와 표시 순서도 저장한다. 로그인, 서버, 클라우드 동기화 없이 작동한다.

첫 버전에 전체·선택·단일 실행, 조건별 분류 이동, 실시간 설정 예시, 실행 전 미리보기, 설정 저장·복원·내보내기·가져오기, 실행 기록, 취소, 버전 자동 증가, Windows/macOS 패키징을 모두 포함한다. 예약 실행·폴더 감시·정규식 편집기·자동 업데이트·완전한 되돌리기는 후속 범위다.

## 2. 기술 선택

| 계층 | 채택 | 선택 이유 및 부담 |
| --- | --- | --- |
| 데스크톱 | Tauri 2 | 시스템 WebView 활용, Rust 네이티브 기능과 웹 UI 분리. OS별 WebView 차이 검증 필요 |
| UI | Svelte 5 + TypeScript | 컴포넌트와 반응형 상태를 간결하게 유지. 이 앱 규모에 전역 상태 라이브러리 불필요 |
| 빌드 | Vite + pnpm | 정적 프런트엔드 빌드. SvelteKit·SSR·Node 서버 불필요 |
| UI 기본 동작 | Bits UI 일부 컴포넌트 | Dialog, 메뉴, Tooltip의 키보드·포커스 처리 재사용. 기본 버튼·입력은 네이티브 HTML |
| 스타일 | CSS 변수 + 컴포넌트 CSS | 작은 디자인 시스템을 직접 소유. 전체 테마 프레임워크를 추가하지 않음 |
| 파일·규칙 엔진 | Rust | 경로, 이동, 검증, 저널, 취소를 하나의 엔진에서 처리 |
| 설정 | 버전 있는 UTF-8 JSON | 프로젝트 규모에 충분하고 내보내기·검토·마이그레이션이 쉬움 |
| 실행 저널 | 파일별 append-only JSONL | 중단 지점 추적. UI 표시용 요약과 분리 |
| 테스트 | Rust tests + Vitest + UI 테스트 | 규칙과 디스크 부작용을 분리해 검증 |

Tauri는 운영체제 WebView를 사용하는 구조다. Svelte는 컴포넌트를 JavaScript로 컴파일한다. 이 특성에 근거해 본 앱의 경량화와 유지관리 요구에 적합하다고 판단했다. **실제 배포 크기·메모리·성능 수치는 구현 후 측정하며 사전에 보장하지 않는다.** [Tauri 구조](https://v2.tauri.app/concept/architecture/), [Svelte 개요](https://svelte.dev/docs/svelte/overview).

Bits UI는 스타일을 강제하지 않는 Svelte용 컴포넌트로 접근성 동작을 제공한다. 사용하는 컴포넌트만 가져오고 앱의 디자인 토큰으로 꾸민다. [Bits UI 공식 소개](https://www.bits-ui.com/docs/introduction).

Windows에는 WebView2가 필요하고 macOS는 WKWebView를 사용한다. 개발에는 Rust와 OS별 네이티브 도구가 필요하다. 이 선택은 웹 UI 작성뿐 아니라 Rust 유지관리도 필요하다는 의미다. [Tauri 사전 준비](https://v2.tauri.app/start/prerequisites/), [프로세스 모델](https://v2.tauri.app/concept/process-model/).

대안 판단: Electron은 개발 생태계가 강점이지만 본 프로젝트는 배포 부담을 우선한다. Flutter는 UI 일관성이 강점이지만 여기서는 웹 기반 컴포넌트 관리와 소규모 CSS 디자인 시스템을 택한다. 이는 제품별 선택이며 절대적인 성능 순위가 아니다.

## 3. 사용자 경험

### 3.1 기본 창

- 처음 실행할 때 창을 최대화한다. 복원 시 기준 크기는 1180×780, 최소 크기는 900×640이며 운영체제 기본 타이틀바를 유지한다.
- 창 제목은 항상 `MoveMgr ver.x.y.z`. 앱 내부 헤더에도 같은 버전을 표시한다.
- 상단: 아이콘·이름·버전, 실행 기록, 설정 가져오기, 내보내기, 프로젝트 추가.
- 본문: 프로젝트 목록. 별도 영구 사이드바 없이 목록에 공간을 집중한다.
- 목록 도구: `전체 선택`, `전체 해제`, `선택 2 / 전체 5`, `미리보기`, 주 실행 버튼.
- 프로젝트 목록은 게시판처럼 고정 열을 가진 표 형태다. 열은 **선택·실행 / 프로젝트명 / 소스 폴더 / 소스 조건 / 타겟 폴더 / 타겟 조건 / 관리** 순서다.
- 프로젝트 하나를 한 줄에 표시하고 행 사이를 선으로 구분한다. 각 셀은 현재 값을 줄임표와 툴팁으로 보여주며, 누르면 해당 항목만 바로 수정한다. 목록은 최대화된 화면 폭을 사용하고 1400px 이상에서는 열 너비·글자·행 높이를 함께 키운다.
- 필수 경로나 조건이 비어 있는 행은 `설정 필요`를 표시하고 단일 실행을 비활성화한다. 해당 행이 전체·선택 실행 범위에 포함되면 상단 미리보기와 실행 버튼도 비활성화한다.
- 실행 중 하단 영역: 처리 파일 수, 바이트 진행률, 현재 프로젝트·파일, 취소 버튼. 완료 후 이동/건너뜀/실패/확인 필요 수와 기록 링크.
- 처음 실행한 빈 목록에는 ‘프로젝트를 추가해 이동 규칙을 만들어보세요’와 추가 버튼.

| 체크 상태 | 주 버튼 | 실행 범위 |
| --- | --- | --- |
| 0개, 프로젝트 존재 | 전체 실행 (N) | 현재 목록의 모든 프로젝트 |
| 1개 이상 | 일부 실행 (K) | 체크된 프로젝트만 |
| 전체 체크 | 일부 실행 (N) | 체크된 전체 프로젝트. 사용자 요구에 따라 ‘일부 실행’ 문구 유지 |
| 프로젝트 없음 | 전체 실행 (0), 비활성 | 없음 |
| 행 단일 실행 | 해당 행의 재생 버튼 | 체크 여부와 무관하게 해당 프로젝트 하나 |

전체 해제는 ‘실행 안 함’이 아니라 전체 실행 상태로 돌아간다는 사실을 도구 영역에 짧게 안내한다. 미리보기도 위와 동일한 선택 범위를 따른다. 체크 변경·순서 변경은 즉시 저장 요청한다. 실행 완료 후에도 체크를 유지한다.

실행 순서는 저장된 목록 순서다. 첫 버전은 앱 전체에서 실행 묶음 하나, 파일 이동 하나씩 진행한다. 실행 중에는 새 실행·프로젝트 편집·가져오기·순서 변경을 잠근다. 내보내기와 기록 조회는 허용한다. 체크 UI도 실행 중 잠가 실행 범위를 혼동하지 않게 한다.

### 3.2 프로젝트 편집

프로젝트의 기본 정보는 목록 행에서 직접 바꾼다. 이름을 누르면 같은 위치가 입력란으로 바뀌고 Enter 또는 포커스 이동으로 저장된다. 소스 폴더와 타겟 폴더를 누르면 각각 OS 폴더 선택기가 열린다. 소스 조건과 타겟 조건 버튼은 필요한 항목만 담은 작은 Dialog를 연다. 프로젝트 전체를 편집하는 별도 창은 사용하지 않는다.

**목록 기본 정보:** 프로젝트명, 소스 폴더 선택, 타겟 폴더 선택. 경로는 목록에서 바로 확인하고 각 영역을 눌러 변경한다.

**1 — 어떤 파일을 옮길까요?**

- 확장자: `모든 파일` 또는 `선택한 확장자`. 사진/동영상/문서 프리셋, 개별 다중 체크, 사용자 확장자 추가.
- 파일명 조건: 기본 ‘제한 없음’. 추가하면 ‘시작 문자열’, ‘포함 문자열’, ‘끝 문자열’, ‘이름 전체 일치’ 중 선택.
- 고급 영역: 하위 폴더 포함(기본 꺼짐), 숨김 파일 포함(기본 꺼짐), 이름 조건 대소문자 무시(기본 켜짐).
- 조건 요약: `jpg 또는 png 중에서 이름이 ABC로 시작하는 파일`.

**2 — 이름에서 무엇을 분류값으로 쓸까요?**

- `이름 전체`, `앞 N글자`, `구분자 앞까지`. 모두 확장자를 제외한 파일명 기준.
- 예: `거래처A_견적서.pdf` → 구분자 `_` 앞 → **거래처A**.
- 구분자는 직접 입력. 여러 번 나오면 첫 등장 기준. 구분자가 없으면 기본 건너뜀, 고급에서 이름 전체 사용 선택 가능.
- ‘앞 N글자’는 사람에게 보이는 글자 단위로 계산한다. 한글·조합 문자·이모지에 일관된 규칙을 사용한다.
- 직접 넣기/고정 하위 폴더에서는 이 단계가 선택 사항으로 표시된다.

**3 — 어디에 넣을까요?**

- `타겟 폴더에 바로 넣기`
- `지정한 하위 폴더에 넣기`: 예 `완료/2026`
- `분류값으로 기존 하위 폴더 찾기`: 비교 방식 선택
- `분류값 이름의 하위 폴더에 넣기`: 없으면 자동 생성

기존 폴더 찾기 선택 시에만 비교 설정을 펼친다. 목적 폴더 예시와 함께 `거래처A_견적서.pdf → 거래처A → D:/보관/거래처A/거래처A_견적서.pdf`를 보여준다.

**하단:** 동명 파일 처리(기본 건너뜀), `실제 파일 미리보기`, `취소`, `저장`. 실시간 예시 1건은 수식 이해용이고 실제 미리보기는 디스크를 읽는 별도 동작이다. 가상 예시를 실제 검색 결과처럼 표시하지 않는다.

### 3.3 실행과 미리보기

`미리보기`는 디스크를 변경하지 않고 계획표를 연다. 열: 프로젝트, 원본 파일, 분류값, 목적 경로, 결과/이유. 이동 가능·충돌·매칭 없음·여러 폴더 일치·실패를 구분하고 페이지 단위로 로드한다.

`전체/일부/단일 실행`은 항상 새 계획을 만든다. 기본 설정 ‘실행 전 미리보기’가 켜져 있으면 계획표에서 `이동 시작`을 누른다. 반복 작업 사용자는 이 설정을 끌 수 있으며 이 경우 같은 검증 후 실행한다. 확인을 끄더라도 모호한 경로·중복 원본 등 차단 항목은 자동 처리하지 않는다.

계획표에 차단 항목이 있으면 이유와 `이동 가능한 항목만 실행`을 제공한다. 원본 중복 소유·소스/타겟 교차처럼 묶음 전체의 의미를 바꾸는 오류는 실행 불가이며 설정 수정이 필요하다. 파일별 매칭 실패나 충돌 건너뜀은 다른 정상 항목의 실행을 막지 않는다.

계획은 설정 revision과 파일 fingerprint를 포함한다. 설정이 바뀌거나 원본 상태가 달라지면 계획을 폐기/재검증한다. 미리보기를 오래 열어두었다고 변경된 파일을 그대로 이동하지 않는다. 실행 직전 목적지 충돌도 재확인한다.

## 4. 조건 규칙: 구현이 달라지지 않도록 확정

### 4.1 파일 선별과 이름 파싱

처리 순서는 `열거 → 확장자 → 파일명 조건 → 분류값 추출 → 폴더 매칭 → 충돌 판단`이다.

- 확장자 목록 내부는 OR, 서로 다른 파일 조건 사이는 AND. 첫 버전은 중첩 AND/OR 편집기를 만들지 않는다.
- `extensions.mode=all`은 전체, `only`인데 목록이 비었으면 저장 불가. 체크를 모두 풀었다고 전체 파일로 바뀌지 않는다.
- 마지막 점 기준 확장자만 사용한다. `a.tar.gz`의 확장자는 `gz`, stem은 `a.tar`. 복합 확장자 패턴은 첫 버전 범위 밖.
- `.gitignore`처럼 선행 점만 있는 이름은 확장자 없음. `파일.`은 확장자 없음이고 stem의 뒤 점을 임의 제거하지 않는다.
- 사용자 입력 `*.JPG`, `.jpg`, `jpg`는 모두 `jpg`로 정규화. 확장자 비교는 ASCII 대소문자 무시. ‘확장자 없음’은 별도 체크.
- 파일명 필터와 분류값은 stem 기준. 원래 파일명·확장자·대소문자는 이동할 때 보존한다.
- 비교 문자열은 Unicode NFC로 정규화한다. N은 정규화 후 Unicode extended grapheme cluster 개수다. 원본 경로를 정규화하여 바꾸지 않는다.
- 대소문자 무시는 locale-independent Unicode case folding으로 비교한다. N글자 자르기는 case folding 이전에 수행한다. 파일·폴더 모두 동일한 엔진을 쓴다.
- 분류값은 기본적으로 앞뒤 공백을 제거한다. 빈 분류값은 건너뜀. 앞 N글자보다 짧은 이름은 `KEY_TOO_SHORT`로 건너뜀.
- 구분자는 비어 있을 수 없고 여러 문자도 허용한다. 첫 등장 위치를 쓴다. 구분자가 맨 앞이면 빈 값으로 처리한다.
- 재귀가 켜져도 디렉터리 자체는 이동하지 않는다. 기본적으로 파일은 목적 폴더에 평탄화하여 모은다. 원본 하위 경로는 자동 보존하지 않는다.
- 심볼릭 링크, junction/reparse 경로는 기본 제외하고 따라가지 않는다. macOS 패키지 디렉터리와 앱 번들 내부도 제외한다. 숨김 판정은 dotfile 및 플랫폼 hidden 속성이다.

### 4.2 타겟 매칭

기존 폴더 탐색은 **타겟 바로 아래 한 단계**로 한정한다. 사용자가 더 아래를 원하면 ‘검색 기준 하위 폴더’를 지정한다. 전체 트리 탐색은 첫 버전에 제공하지 않는다.

폴더명도 `이름 전체 / 앞 M글자 / 구분자 앞`으로 폴더 비교값을 만들 수 있다. 기본값은 폴더 이름 전체이다. 파일의 분류값은 `K`, 폴더 비교값은 `F`다.

| UI 표현 | 정확한 의미 | 예시 |
| --- | --- | --- |
| 분류값과 정확히 같음 | normalize(K) = normalize(F) | K=`ABC`, F=`ABC` 일치, `ABC 자료` 불일치 |
| 분류값으로 시작함 | F가 K로 시작 | K=`ABC`, F=`ABC 자료` 일치 |
| 양쪽 앞 N글자가 같음 | K와 F 모두 N글자 이상이며 앞 N글자 일치 | K=`ABC2026`, F=`ABC 고객`, N=3 일치 |

`앞 N글자`와 `정확히 같음`을 조합하면 ‘파일 앞 3글자 ABC와 폴더 전체 ABC가 같은 경우’도 표현할 수 있다. 폴더 추출을 ‘구분자 앞’으로 설정하면 `ABC_고객명` 폴더도 정확 일치 규칙으로 찾을 수 있다.

매칭 1개면 이동한다. 0개면 기본 건너뜀이며, 옵션으로 검색 기준 폴더 아래에 분류값 이름의 폴더를 생성할 수 있다. 2개 이상이면 `AMBIGUOUS_TARGET`으로 해당 파일을 보류한다. **정렬의 첫 폴더를 임의 선택하지 않는다.**

경로 조합은 OS Path API로 처리한다. 고정 하위 경로는 루트 내부의 상대 경로만 허용한다. 분류값을 폴더 이름으로 쓰는 경우 `/`, `\`, `..`, 제어 문자, Windows 예약 이름·금지 문자·후행 점/공백을 검증한다. 플랫폼 사이에서 다르게 해석되는 이름을 조용히 치환하지 않고 이유를 표시한다. 경로 전체 길이는 실제 대상 파일시스템의 결과로 판정한다.

### 4.3 대표 사용 예

| 소스 파일 | 파일 조건·분류값 | 목적지 규칙 | 결과 |
| --- | --- | --- | --- |
| `사진.jpg`, `사진.png` | jpg/png | 바로 넣기 | 두 파일 모두 타겟 루트로 이동 |
| `ABC_001.pdf` | pdf, 이름이 ABC로 시작, 앞 3글자 | 폴더 전체와 정확 일치 | `타겟/ABC/ABC_001.pdf` |
| `ABC_001.pdf` | `_` 앞 → ABC | 폴더가 분류값으로 시작 | `타겟/ABC 고객/ABC_001.pdf` |
| `ABC2026_보고서.pdf` | `_` 앞 → ABC2026 | 양쪽 앞 3글자 비교 | `타겟/ABC 보관/ABC2026_보고서.pdf` |
| `거래처A_견적서.pdf` | `_` 앞 → 거래처A | 폴더도 `_` 앞을 추출, 정확 일치 | `타겟/거래처A_2026/거래처A_견적서.pdf` |

## 5. 파일 이동 안정성

파일 이동은 되돌릴 수 없는 중간 상태가 있으므로 이 부분은 구현의 핵심 기능이다.

### 5.1 시작 전

- 설정 유효성, 실제 경로, 읽기·쓰기 권한, 가능한 디스크 여유 공간을 확인한다. 미리보기는 쓰기 테스트용 파일도 만들지 않는다. 사전 권한 검사는 참고이며 실제 작업 오류를 반드시 처리한다.
- 같은 프로젝트의 소스와 타겟이 동일하거나 어느 한쪽이 다른 쪽 내부면 차단한다. symlink/junction/별칭을 해석한 실제 경로 기준으로 검사한다.
- 한 실행 묶음에서 서로 다른 프로젝트의 소스 범위가 겹치거나 타겟이 다른 프로젝트의 소스 범위와 교차하면 차단한다. 순차 실행 중 다시 주워가는 연쇄 이동을 허용하지 않는다.
- 여러 프로젝트가 같은 타겟을 쓰는 것은 가능하다. 최종 파일 경로 충돌은 묶음 전체에서 예약하여 목록 순서대로 처리한다.
- 경로 문자열만으로 비교하지 않는다. 파일시스템의 case sensitivity와 파일 ID/volume identity를 가능한 범위에서 사용한다. 동명 hard link 원본의 중복 실행도 판정한다.
- 실행 전 모든 원본 목록을 고정한다. 실행 중 새로 생긴 파일은 다음 실행 대상으로 남긴다.
- 사용 중이거나 외부에서 쓰는 파일은 잠금/재검증 실패 시 건너뛴다. 기본적으로 스캔 시점과 실행 직전 크기·mtime·파일 ID를 확인한다. 무제한 자동 재시도하지 않는다.

### 5.2 충돌 정책

첫 버전은 `건너뛰기`와 `번호 붙이기`를 제공한다. 기본은 건너뛰기다. 덮어쓰기는 첫 버전에 포함하지 않는다.

번호 붙이기는 `파일 (1).ext`, `파일 (2).ext` 순으로 제안하며, 실행 시 no-clobber 방식으로 이름을 확정한다. 이미 존재하는 파일·디렉터리·끊어진 링크도 이름을 점유한 것으로 본다. 계획 이후 다른 프로세스가 같은 이름을 만들면 다시 충돌 정책을 적용하고 실제 최종 경로를 기록한다. 미리보기와 달라졌음을 결과에 표시한다.

### 5.3 실제 이동

동일 파일시스템: 원본 ID와 경로를 재검증하고, 기존 목적지를 대체하지 않는 OS별 rename/move 연산을 사용한다. `exists()` 검사 후 일반 `rename()`을 하는 것으로 no-clobber를 보장했다고 간주하지 않는다. 플랫폼 adapter에 해당 의미를 구현하고 통합 테스트한다.

서로 다른 파일시스템: 아래 순서를 지킨다.

1. 실행 저널에 원본·예정 경로·ID와 상태를 기록하고 flush한다.
2. 타겟 폴더 내부에 배타적으로 생성한 `.movemgr-<run>-<item>.part`로 복사한다.
3. 복사 중 소스 SHA-256을 계산하고, 완료 후 타겟 임시 파일을 다시 읽어 해시와 크기를 검증한다. 필요한 flush/sync를 수행한다.
4. 원본의 ID·크기·mtime을 다시 검사한다. 가능한 OS 잠금을 사용한다. 안정적으로 읽을 수 없으면 원본을 유지하고 확인 필요로 끝낸다.
5. 임시 파일을 최종 이름으로 no-clobber 확정한다. 확정 사실을 저널에 영속 기록한다.
6. 원본 경로가 여전히 같은 파일인지 다시 확인하고 원본을 삭제한다. 삭제 성공을 기록해야 `moved`다.

최종 파일 생성 후 원본 삭제에 실패하면 **복사 완료·원본 남음**(`sourceRetained`)이다. 성공한 이동으로 합산하지 않는다. 자동 재실행으로 중복 파일을 더 만들지 않도록 기록을 조회하고 사용자에게 원본 확인을 안내한다.

두 볼륨 사이 복사/삭제를 하나의 원자적 트랜잭션으로 만들 수 없다는 점을 상태 설계에 반영한다. 악의적인 외부 동시 수정이나 모든 네트워크 파일시스템에서 완벽한 스냅샷을 보장한다고 주장하지 않는다. 식별과 안정성을 보장할 수 없는 경우 원본 삭제를 보류한다.

이동의 기본 보장 범위는 파일의 본문 바이트다. 동일 볼륨 rename은 OS 메타데이터를 유지한다. 볼륨 간 복사는 수정 시각·기본 권한을 가능한 범위에서 보존하며, NTFS ADS·macOS resource fork/xattr 같은 추가 스트림이 있는 파일은 첫 버전에서 해당 항목을 감지할 수 있는 adapter를 마련해 `UNSUPPORTED_METADATA`로 보류한다. 감지/보존을 검증하지 못한 파일시스템에서도 조용한 정보 손실 대신 보류한다.

### 5.4 중단·오류·복구

- 취소는 다음 안전 지점에서 적용한다. 복사 중이면 복사를 멈추고 원본을 유지한다. 이미 최종 파일이 확정된 항목은 단계에 맞게 정리하거나 확인 필요로 기록한다.
- 이미 이동 완료된 파일은 취소로 원복되지 않는다. 종료 버튼에는 실행 중일 때만 ‘취소 후 종료/계속 실행’을 표시한다.
- 파일별 잠금·권한·매칭 실패는 기록하고 계속 진행한다. 타겟 볼륨 제거·공간 부족·저널 쓰기 실패는 해당 실행을 중단한다.
- 정상 종료 시 앱이 소유한 현재 임시 파일만 정리한다. 다른 `.part` 파일을 패턴만 보고 삭제하지 않는다.
- 재시작 시 미완료 저널을 확인하고 `중단된 실행 확인` 화면을 제공한다. 파일 존재 여부·ID·해시를 대조해 moved/sourceRetained/notMoved/needsReview로 판정한다. 자동으로 원본을 삭제하거나 새 이동을 이어가지 않는다.
- 첫 버전은 전체 되돌리기를 제공하지 않는다. 실행 결과에서 원본·최종 위치와 처리 이유를 확인할 수 있다.

## 6. 저장·가져오기·내보내기

설정은 Tauri의 OS별 app config 디렉터리에 저장한다. OS 표준 위치를 API로 구하고 사용자명이나 드라이브를 하드코딩하지 않는다. 저장은 Rust 단일 writer, 임시 파일→flush→검증→기존 파일 교체 방식으로 수행하며 이전 정상본 1개를 유지한다. Windows 파일 교체 API 동작도 검증한다.

프로젝트 CRUD·체크·순서는 즉시 저장 요청 후 성공 확인한다. 창 크기 같은 잦은 변경은 300ms debounce하고 정상 종료 때 flush한다. ‘저장됨’ 표시는 쓰기 완료 응답 후에만 보여준다. 실패는 지속 표시하고 미저장 상태를 유지한다.

가져오기는 JSON 파싱→형식·schemaVersion 검증→마이그레이션→변경 요약→적용 순서다. `기존 설정 교체`와 `프로젝트 추가`를 제공한다. 교체는 기존 설정 자동 백업 후 적용하고 앱 공통 설정·체크·순서도 가져온다. 추가는 가져온 프로젝트에 새 UUID를 부여하고 기존 목록 뒤에 붙인다. 같은 이름은 `(가져옴 1)`처럼 구분한다. 추가 가져오기는 기존 앱 공통 설정을 유지한다.

내보내기는 전체 설정을 UTF-8 JSON으로 저장한다. 경로·규칙·체크·순서·테마·미리보기 설정을 포함하며 실행 저널과 창 위치는 제외한다. 프로젝트 선택 실행 체크 상태를 내보내기 범위 선택으로 재사용하지 않는다.

다른 OS에서 가져온 경로는 그대로 보존하되 `경로 다시 지정 필요`로 표시한다. 가져오기 마지막 단계에서 소스/타겟별 폴더 재연결과 접두 경로 일괄 매핑을 제공한다. 예: `D:/작업` → `/Users/me/Work`. 드라이브 문자를 임의로 macOS 경로로 변환하지 않는다. 없는 경로를 가진 프로젝트도 저장할 수 있으나 실행 시 차단한다.

미지원 미래 schemaVersion은 적용하지 않는다. 깨진 설정은 원본을 보존하고 정상 백업 복구/파일 선택을 제안한다. 앱 버전과 설정 schemaVersion은 서로 독립이다. 가져오기 파일 상한은 10MiB로 하고 초과하면 변경 없이 오류를 표시한다.

## 8. 구조와 책임

```text
Svelte 화면 / 설정 초안 / 상태 표시
              ↕ typed IPC (commands + events)
Rust application: 설정 · plan · run · history
              ↕
Rust domain: 필터 · 분류값 · 폴더 비교 · 충돌 규칙
              ↕
Rust infrastructure: 디스크 · OS별 no-clobber · 저장 · 저널
```

프런트엔드에서 임의 파일 이동 API를 호출하지 않는다. Rust가 전달된 프로젝트 ID로 저장 설정을 읽고 허용된 루트·경로·plan을 검증한다. 초안 미리보기는 초안을 검증한 임시 계획으로 만들며 실행할 수 없다. 모든 custom command에서 자체 검증을 하고 Tauri capability만으로 Rust 파일 접근이 제한된다고 가정하지 않는다. [Tauri 보안 모델](https://v2.tauri.app/security/).

조건 예시 계산도 Rust 순수 함수를 IPC로 호출하여 실제 실행과 일치시킨다. UI 계산 복사본은 만들지 않는다. 디스크 작업은 UI 스레드를 막지 않는 worker에서 실행하고 진행 이벤트를 100~200ms 단위로 모은다. 진행률은 파일 수·현재 바이트로 표시하고 완료 전에는 추정 시간을 확정값처럼 보여주지 않는다.

설정 저장·실행·가져오기는 전역 coordinator에서 직렬화한다. 앱은 single-instance로 동작한다. 새 실행 명령이 이미 실행 중이면 backend에서도 거부한다.

## 9. 버전 관리와 빌드

버전 형식은 `major.minor.patch`. 최초 구현 빌드는 **0.0.1**. UI·로직·의존성·아이콘 등 실행 결과가 달라지는 수정 빌드마다 **patch만 자동으로 1 증가**한다. major/minor는 사용자 명시 지시가 있을 때만 변경하고 patch를 0으로 재설정한다. 앱 실행이나 사용자 설정 저장으로 버전을 올리지 않는다.

자동 증가 단위는 소스 변경 묶음의 ‘빌드 준비’다. 파일을 저장할 때마다/HMR 때마다 증가시키지 않는다. 동일 소스의 Windows/macOS 빌드는 같은 버전을 사용한다.

구현할 방식:

1. 저장소 루트 `version.json`을 버전의 단일 기준으로 둔다. `{version, sourceDigest, schemaVersion:1}`. 첫 빌드에서 version=0.0.1과 digest를 확정한다.
2. Node 기반 `prepare-build.mjs`가 앱 소스·설정·의존성 lockfile·아이콘·빌드 스크립트의 정렬된 경로+바이트로 SHA-256 digest를 계산한다. 절대 경로·mtime은 넣지 않는다. docs, copy, dist, target, .git, 생성된 버전 파일은 제외한다. 줄바꿈은 `.gitattributes`로 고정한다.
3. 이전 digest와 다르면 patch를 한 번 올리고 manifest와 Cargo/package/Tauri 버전 및 lockfile을 함께 동기화한다. 생성된 버전 필드 때문에 digest가 다시 바뀌지 않도록 manifest의 버전 관련 필드는 제외/정규화한다.
4. 준비 단계는 파일 잠금으로 직렬화한다. 실패해 이미 할당된 번호는 재사용하며, 같은 digest의 재시도는 재증가하지 않는다. 수정해 digest가 바뀌면 새 번호를 부여한다.
5. `pnpm dev`와 로컬 패키징 진입점에서 준비 단계를 호출한다. 실행 중 HMR은 앱 헤더에 ‘개발 중 변경’ 표시가 가능하되 새 버전 확정은 다음 준비 단계에서 한다.
6. CI는 한 준비 job이 manifest와 버전을 확정한 소스 스냅샷을 만들고, Windows/macOS jobs는 그 동일 스냅샷을 읽기 전용으로 빌드한다. jobs 각각에서 증가시키지 않는다. 릴리스 준비는 한 release 브랜치/직렬화된 workflow에서만 수행하며 version manifest를 저장소에 반영한다.
7. 타이틀바·내부 헤더·설정 내보내기의 앱 버전·포터블 실행 파일 메타데이터가 모두 일치하는지 CI에서 검사한다. 더 자세한 정보 화면에는 commit/digest·OS·빌드 시각을 별도로 표시한다.

직접 `cargo build`/`tauri build`를 호출해 버전 준비를 우회하는 빌드는 배포 금지다. CI의 version check가 오래된 digest를 실패 처리해야 한다. 수동 상위 버전 변경은 `version:set 0.1.0`처럼 명시적 명령으로 구현하고 자동 증가 스크립트와 분리한다.

공통 소스를 **Windows runner와 macOS runner에서 각각 빌드**한다. Windows PC 하나에서 macOS 서명 패키지까지 모두 생산하는 것을 전제로 삼지 않는다. 공식 Tauri GitHub Actions 패턴을 참고한다. [공식 빌드 파이프라인](https://v2.tauri.app/distribute/pipelines/github/).

| 산출물 | 빌드 환경 | 목표 |
| --- | --- | --- |
| Windows 포터블 폴더 (`MoveMgr.exe`) | Windows, MSVC | x64 우선, Windows 10/11 검증 |
| macOS DMG / app | macOS, Xcode 도구 | Apple Silicon 및 Intel 별도 패키지, macOS 13+를 제품 지원 목표로 검증 |

지원 OS는 제품의 검증 범위이며 프레임워크의 최소 지원 버전과 구분한다. Windows는 설치 과정 없이 포터블 폴더에서 직접 실행하며 Windows 10/11의 WebView2 Runtime을 사용한다. Windows ARM64와 macOS universal 묶음은 추가 검증 후 선택한다. 공개 배포용 코드 서명 및 macOS 공증은 별도의 배포 설정으로 마련하고 자격 증명은 CI secret으로 관리한다.

## 10. 설계상의 기본값

질문을 반복하지 않고 구현할 수 있도록 다음을 기본값으로 확정했다: 한국어 UI, 시스템 테마, 비재귀 검색, 숨김·링크 제외, 직접 하위 폴더 매칭, 이름 대소문자 무시, 실행 전 미리보기 켜짐, 충돌 건너뜀, 매칭 실패 건너뜀, 모호한 폴더 보류, 프로젝트·파일 순차 처리, 완료 후 체크 유지. 사용자가 후속 지시하면 변경한다.
